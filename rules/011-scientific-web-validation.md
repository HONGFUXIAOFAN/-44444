# 011-科学性联网验证

> 对配方参数进行多来源联网交叉验证，确保科学性、真实性、安全性，杜绝 AI 幻觉配方。

---

## 目的

联网搜索多个独立来源，交叉验证 010 规则生成的配方参数的准确性和安全性，确保用户拿到的配方可以放心使用。

---

## 触发器

**WHEN** 010-配方参数生成获得用户确认后。

---

## 输入

- 010 规则产出且用户已确认的**配方参数表**

---

## 行为

### 步骤1：逐项验证配方参数

对配方中的每一项执行验证：

#### 1.1 原料种类验证
- 联网搜索该菜品的标准配料表
- 确认配方中每种原料是否为该菜品的常规配料
- 标记异常原料（不该出现但出现了 / 该出现但缺失了）

#### 1.2 用量比例验证
- 验证各原料用量是否在合理范围内
- 对比 ≥2 个独立来源的用量数据
- 用量偏差 >30% 的标记为"需人工确认"

#### 1.3 食品安全验证
- 检查是否存在相克原料组合
- 检查是否有超量使用的不安全原料
- 验证烹饪温度是否达到食品安全要求（如肉类中心温度 ≥75℃）

#### 1.4 可行性验证
- 验证操作温度是否合理（如炒糖色 180-200℃、油炸 160-180℃）
- 验证时间参数是否符合烹饪常识（如卤牛肉 60-90 分钟）
- 验证原料的可用性（是否存在极其罕见或难以获取的原料）

### 步骤2：生成验证报告

```markdown
## 【科学性验证报告】

### 验证概览
| 验证维度 | 结果 | 置信度 | 依据来源数 |
|---------|------|--------|-----------|
| 原料种类 | ✅/⚠️/❌ | % | N |
| 用量比例 | ✅/⚠️/❌ | % | N |
| 食品安全 | ✅/⚠️/❌ | % | N |
| 操作可行性 | ✅/⚠️/❌ | % | N |

### 详细验证记录

#### ✅ 通过项（N项）
| 原料 | 配方用量 | 参考范围 | 来源 |
|------|---------|---------|------|

#### ⚠️ 需确认项（N项）
| 原料 | 配方用量 | 参考范围 | 偏差 | 建议 |
|------|---------|---------|------|------|

#### ❌ 问题项（N项）
| 原料 | 问题描述 | 建议整改 |
|------|---------|---------|

### 验证结论
- 总体置信度：{X}%
- 可直接使用：{是/否}
- 需调整项数：{N}
```

### 步骤3：处理验证结果

| 结论 | 行动 |
|------|------|
| 全部通过（置信度 ≥90%） | 直接进入下一步（012-操作流程生成） |
| 有需确认项 | 标注疑问，向用户解释风险，等用户决定 |
| 有问题项 | 自动修正后重新验证，或向用户建议替代方案 |

### 步骤4：等待用户确认

```
【科学性验证完成】

✅ 通过：{N}项 | ⚠️ 需确认：{N}项 | ❌ 不通过：{N}项

{如有需确认/不通过项，逐项列出问题和建议}

请确认：
1. ⚠️标记的项是否需要调整？
2. 总体配方参数是否可以进入操作流程生成？

```

## 2026-10-26补充：A/B分别验证

- A、B两个版本必须分别核验关键原料、用量范围、食品安全条件和工艺依据；不得以A版的证据自动替代B版。
- 重点验证两版有意改变的参数及其预期机制，并说明证据是直接研究、相近食品外推、行业资料还是供应商资料。
- 公开资料支持设计方向，不等于证明该门店的最终风味结果；没有现场数据时不得写成“已实测有效”。
- 若某项证据不足，仍应给出当前最有依据的候选设计，并清楚标注不确定性；不得把“用户去实验”作为本阶段完成工作的替代方案。

## 规则约束

- **禁止**：跳过联网验证，直接信任 AI 生成的配方参数
- **要求**：每个维度至少查询 2 个独立来源
- **要求**：验证报告必须透明展示所有验证项的来源
- **注意**：如网络搜索无法获取足够信息，诚实告知用户并标注置信度降低

### 格式自检清单（输出前逐项检查）

- [ ] 验证报告包含四维度（原料种类/用量比例/食品安全/操作可行性）
- [ ] 每个维度有置信度百分比和依据来源数
- [ ] 通过项/需确认项/问题项 三类已逐项列出
- [ ] 验证结论包含总体置信度和是否可直接使用的判断

---

## 输出

- **科学性验证报告**：四维度验证结果 + 问题项清单 + 整改建议
- **用户确认记录**：用户对验证结果的确认
