# 240-人类反馈分析

> 基于RCA框架分析用户反馈，识别配方方案中的问题根因，生成结构化分析报告，驱动方案迭代改进。

---

## 目的

对用户在审查确认环节（030规则）或交付后提出的反馈意见，进行结构化分析，区分症状与根因，产出可执行的改进方案，确保每次迭代都有据可依。

**核心价值**：
- **不猜测**：所有结论基于用户反馈原文和方案证据，不凭空推测
- **深挖根因**：不只是"改这里"，而是找出"为什么这里会出问题"
- **可追溯**：每次反馈分析生成独立报告，迭代历史清晰可查

---

## 触发器

**WHEN** 用户对已生成的配方方案提出反馈意见时。

**典型场景**：
- 用户指出配方参数不符合预期（"这个用量不对""原料有遗漏"）
- 用户对操作流程提出质疑（"这个步骤不现实""时间估算偏差大"）
- 用户对文档内容/结构/措辞不满意（"缺少某声明""某部分应放前面"）
- 用户提出新增/删除/调整需求

---

## 输入

### 必需输入
- **用户反馈原文**：用户的完整反馈文本
- **涉及产出物**：被反馈的配方方案文档 / 规则产出物

### 可选输入
- **涉及规则文件**：被反馈内容对应的生成规则（如010/012/030等）

---

## 行为

### 步骤0：思考与规划（向用户汇报，等待确认）

1. 读取用户反馈，初步识别：
   - 反馈涉及哪些规则/模块（配方参数/操作流程/成本/地域适配/添加剂/文档格式等）
   - 问题类型初步判断
2. 规划分析流程，向用户汇报：
   ```
   【240反馈分析 - 初步识别】
   - 反馈来源：用户审查反馈
   - 涉及模块：{模块列表}
   - 问题类型：{功能缺失/质量不足/格式问题}
   - 分析方向：{初步假设}

   确认后进入RCA根因分析。
   ```

### 步骤1：Problem Definition（问题定义）

将用户的主观反馈转化为客观问题：

| 维度 | 说明 |
|------|------|
| 问题描述 | 客观描述问题（非主观感受） |
| 问题分类 | 配方数据错误 / 流程缺失 / 内容遗漏 / 结构不当 / 格式问题 / 措辞不当 |
| 涉及规则 | 定位到具体规则ID和章节 |
| 影响范围 | 仅当前文档 / 影响后续所有产出 |
| 严重程度 | 🔴阻塞（无法使用）/ 🟡影响体验 / 🟢微调建议 |

### 步骤2：Evidence Collection（证据收集）

1. 引用用户反馈原文（完整引用）
2. 定位当前方案中的对应位置（截取问题段落）
3. 对照相关规则要求（检查是否符合规则标准）

### 步骤3：Root Cause Identification（根因识别）

1. **区分症状与根因**：
   - 症状：用户看到的问题表现
   - 根因：导致问题的底层原因
2. **应用5 Whys**：逐层追问"为什么"，直到找到根本原因
3. **根因分类**：
   - 规则设计缺陷（规则本身不完善）
   - 规则执行偏差（未严格按规则执行）
   - 用户需求未对齐（前期确认不充分）
   - 外部信息不足（联网搜索数据不准确）

### 步骤4：Recommendation（改进建议）

对每个根因提出可执行建议：

| 字段 | 说明 |
|------|------|
| 改进方向 | 具体改什么 |
| 涉及文件 | 需修改的规则文件 / 方案文档 |
| 改进步骤 | 分步操作说明 |
| 验收标准 | 改完后怎样算通过 |

### 步骤5：执行改进

按建议执行修改，修改后向用户确认。

---

## 规则约束

- **禁止**：跳过根因分析直接修改——必须先找出"为什么"
- **禁止**：在用户未确认分析结果前执行修改
- **要求**：每条反馈独立分析，逐个处理
- **要求**：修改后必须告知用户改了什么、为什么这样改
- **注意**：如果反馈涉及多个独立问题，逐条分析、逐条处理

---

## 输出

- **反馈分析报告**：步骤0-4的完整分析（对话中输出，无需单独文件）
- **改进执行记录**：具体修改了什么（在修改后的确认信息中体现）
