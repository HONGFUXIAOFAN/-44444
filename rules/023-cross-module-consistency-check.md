# 023-跨模块逻辑一致性校验

> 在全部内容模块（010配方参数/012操作流程/014通俗原理）生成完成后，强制进行三向一致性校验。确保配方方案不是各自独立模块的堆砌，而是一个前后一致、逻辑自洽的有机整体。

---

## ⛔ 强制执行声明

> **本规则是 P0 级强制门禁。023 未通过 = 方案不合格 = 禁止进入 022。**

---

## 目的

**配方方案的前后矛盾是最低级但最致命的错误**——用户看到"香料全部打粉"和"丁香不能打碎"同时出现时，整个方案的可信度归零。

本规则的核心任务：
1. 校验 010（配方参数表）、012（操作流程）、014（通俗原理）三份产出之间的一致性
2. 确保每个原料的处理方式在三份产出中描述一致
3. 确保每个知识点的操作指引有明确落地、无矛盾
4. 发现不一致 → 标记 → 回退修改 → 重新校验，直到全部通过

---

## 触发器

**WHEN** 014-科学原理通俗化注入完成并用户确认后。

---

## 输入

- 010 规则产出的**配方参数表**（含原料清单、用量、预处理方式）
- 012 规则产出的**标准化操作流程**
- 014 规则产出的**嵌入通俗原理的操作流程**

---

## 行为

### 步骤1：提取三份产出中的关键实体

从三份产出中提取所有"可对比实体"：

| 实体类型 | 提取来源 | 示例 |
|---------|---------|------|
| 原料名称 | 010 配方参数表 | 丁香、草果、八角、花椒... |
| 原料预处理方式 | 010 配方参数表 | "打粉""拍裂""整粒""切末" |
| 操作步骤中的处理方式 | 012 操作流程 | "香料全部打成细粉""丁香整粒放入" |
| 通俗原理涉及的操作 | 014 通俗原理 | "丁香打碎会发苦，所以要整粒用" |
| 添加剂名称及用量 | 010 + 012 + 021 | 名称/用量/添加时机一致性 |

### 步骤2：逐实体三向对比（核心步骤）

对每个实体，建立对比矩阵：

```
实体：{原料名称}
┌──────────┬─────────────────────┬─────────────────────┬─────────────────────┐
│   来源    │ 010-配方参数表       │ 012-操作流程          │ 014-通俗原理          │
├──────────┼─────────────────────┼─────────────────────┼─────────────────────┤
│ 预处理方式 │ {010中的处理方式}    │ {012中的处理方式}    │ {014中的处理方式}    │
│ 是否一致   │ ✅/❌               │ ✅/❌               │ ✅/❌               │
└──────────┴─────────────────────┴─────────────────────┴─────────────────────┘
```

**判定规则**：
- 三向全部一致 → ✅ 通过
- 任两方一致、第三方未提及 → ⚠️ 需补充（第三方必须明确说明）
- 两方矛盾 → ❌ 阻塞，必须回退修改
- 一方有定义、另两方未提及 → ⚠️ 需补充（另两方必须同步）

### 步骤3：专项逻辑校验

除原料逐项对比外，还需检查以下跨模块逻辑链：

#### 3.1 数量一致性
- 010 配方参数表中的原料总数 = 012 操作流程中涉及的原料总数？
- 如有"预留"或"分次加入"的原料，012是否明确标注？

#### 3.2 顺序一致性
- 012 操作流程中原料的加入顺序，是否与 010 中的"预处理方式"兼容？
- 例：010 说"提前浸泡4小时"的原料，012 是否在流程开始前安排了浸泡步骤？

#### 3.3 温度/时间一致性
- 010/012 中的关键温度参数（烫漂温度、油温、炖煮时间等）是否一致？
- 014 通俗原理中引用的温度数字是否与 012 一致？

#### 3.4 添加剂使用一致性
- 021 推荐的添加剂在 012 操作流程中是否有明确的"何时加入、怎么加入"？
- 添加剂用量在 010 配方表和 021 安全卡中是否一致？

#### 3.5 "说了就教了"原则
- 010 中列出的每种原料，012 中是否都有明确的操作指引？
- 014 中解释的每个"为什么"，012 中是否有对应的"怎么做"？
- **禁止**：010 列了原料但 012 没教怎么处理（如"草果"列了但没说要不要拍裂）

### 步骤4：生成一致性校验报告

```markdown
## 【023-跨模块逻辑一致性校验报告】

### 一、三向对比总览

| 序号 | 原料 | 010-处理方式 | 012-操作描述 | 014-原理说明 | 一致性 | 
|:----:|------|-------------|-------------|-------------|:---:|
| 1 | 丁香 | 整粒 | 整粒放入香料包 | 丁香打碎会发苦 | ✅ |
| 2 | 草果 | 拍裂 | 刀背拍裂后放入 | —（未提及） | ⚠️ 014需补充 |
| 3 | ... | ... | ... | ... | ... |

### 二、问题汇总

| 问题编号 | 严重程度 | 涉及实体 | 问题描述 | 涉及模块 | 修改建议 |
|:--------:|:---:|---------|---------|---------|---------|
| C-001 | 🔴 | 草果 | 014未解释草果为何要拍裂 | 014 | 补充通俗原理 |
| C-002 | 🔴 | 香料全族 | 010说"全部打粉"，但丁香/草果不能打 | 010/012 | 按012实际处理方式修正010 |
| ... | ... | ... | ... | ... | ... |

### 三、校验结论

- 全项通过：{X} 项
- 需补充：{Y} 项
- 阻塞（必须修改）：{Z} 项

总计：{X+Y+Z}/{总检查项}
```

### 步骤5：根据校验结果处理

| 校验结果 | 处理方式 |
|---------|---------|
| 全项 ✅ | 进入步骤6，等待用户确认 |
| 有 ⚠️ | 列出需补充项，用户确认后回退补充 |
| 有 ❌ | **阻塞**——列出所有矛盾项+修改建议，回退到对应规则修改，修改后重新执行023 |

### 步骤6：等待用户确认

```
【023-跨模块逻辑一致性校验完成】

校验范围：{N} 个原料 × 3 个模块 = {M} 项对比

一致性结果：
- ✅ 全项通过：{X} 项
- ⚠️ 需补充：{Y} 项
- ❌ 矛盾阻塞：{Z} 项

{如有问题，逐条列出}

请确认校验结果。通过后进入【024-配方整体科学协同性验证】。
```

## 2026-10-26补充：A/B分别校验与有意差异识别

- 对A、B两个版本分别建立010↔012↔014三向矩阵；不得用单一版本的检查结果代表另一版本。
- 先从010中提取每个版本的最终参数，再核对012和014中的引用。若A、B某项数字不同，只要这是经说明的有意设计差异，就不判为矛盾。
- 同一版本内，同一原料在配方表、流程、添加剂卡、分装表和速查卡中的完整用量必须一致；如为分次加入，必须明确每次用量并核对分次合计。
- 配方优化阶段允许变更数字；本规则不要求恢复原配方数字，也不要求A、B总重相同。
- 031导出前还须进行全文件最终数值审计；023的模块一致性检查不能替代该审计。

## 规则约束

- **禁止**：在存在 ❌ 矛盾项的情况下继续后续步骤
- **禁止**：只对比而不回看原文——每条对比必须引用三份产出中的原文位置
- **要求**：010列出的每个原料，012中必须有操作说明，014中必须有原理说明（或明确标注"无特殊原理"）
- **要求**：校验报告必须包含"修改建议"，不能只指出问题不给出方案
- **要求**：重新修改后必须重新执行023全量校验（不可只检查修改项）

### 格式自检清单（输出前逐项检查）

- [ ] 三向对比表覆盖 010 配方参数表中的所有原料
- [ ] 每个不一致项标注了涉及模块和修改建议
- [ ] 添加剂用量在 010/012/021 中三方一致
- [ ] 温度/时间参数在 010/012/014 中三方一致
- [ ] 每个原料的预处理方式在三个模块中一致
- [ ] 校验结论明确（✅通过 / ⚠️需补充 / ❌阻塞）
- [ ] 存在❌时已明确回退路径
